# 接口架构规范（目标态）

> 状态：Controller 六条硬性禁则已在现有代码实施；资源命名、列表形态、统一返回、错误模型等其余部分仍为目标态，未全面实施。本文用于确认接口层目标架构，并作为 Controller 设计、评审和新增接口的依据；未实施部分不能当作现状接口清单。
>
> 适用范围：`aio-life-server` 的 HTTP 业务接口，以及 Web、Mobile 的调用契约。
>
> 与其他文档的关系：分页、日期、ID、契约生成和统一推送的细节以 [API 参数规范](API参数规范.md) 为准；请求和响应的最小字段以 [接口最小信息契约](接口最小信息契约.md) 为准。本文补充资源划分、URL、方法语义、错误模型、Controller 边界和架构守护规则。

## 1. 目标与评价标准

接口层的目标不是追求最高的 REST 纯度，而是在“两端客户端 + 契约自动生成 + 小团队 + 未上线”的约束下，让接口满足四项要求：

1. **可预测**：同类资源的结构一致，调用方不需要为每个模块记忆一套写法。
2. **可生成**：请求、查询、响应模型能被 OpenAPI 和契约生成器准确表达。
3. **可守护**：架构约束由测试（ArchUnit、契约测试）保证，而不是依赖 code review。
4. **可演进**：新增资源、拆模块、换客户端时不需要改动公共约定。

四项要求的优先级高于“REST 教科书写法”。凡两者冲突，以客户端能力、契约可生成性和团队可维护性为准。

### 1.1 现状与目标的总体差异

| 主题 | 现状示例 | 目标 |
| --- | --- | --- |
| 资源路径 | camelCase、kebab-case、单复数混用 | 统一 kebab-case 复数 |
| 列表入口 | 根路径、`/query`、`/page`、`/list`、`/all` | 管理列表、`/options`、`/{id}` |
| 更新 | `PUT /资源`（ID 在 body）或 `PUT /资源/{id}` | `PUT /资源/{id}` |
| 写操作返回 | VO、`Boolean`、`Void`、新 ID 字符串 | VO；删除 `Void`；批量 `BatchResult` |
| 删除 | `DELETE /{id}`、`/batchDelete`、`/deleteBatch` | `DELETE /{id}`、`POST /batch-delete` |
| 状态与排序 | `pin`、`toggleTop`、`reSort`、`pinned-order` | `PUT /{id}/pin`、`PUT /order` |
| 管理端 | 独立 Controller、`/admin` 子路径、同路径方法级鉴权 | `XxxAdminController` + `/system/*` |
| 错误 | 抛异常与 `ApiResponse.error` 混用 | 领域异常 + 全局 advice |
| 分页 | `PageResp` 与 `List` 混用 | 管理列表统一 `PageResp` |
| 查询模型 | `CommonQuery<T>` 与新式 Query DTO 混用 | 具体 Query DTO |
| 文件响应 | `HttpServletResponse`、`ResponseEntity<Resource>`、`ResponseEntity<byte[]>` | `ResponseEntity<Resource>` 统一封装 |
| 当前用户 | Controller 调用 `StpUtil` | `@CurrentUserId` 参数注入 |
| ID | `long`、`Long`、`String` 混用 | 边界统一 `String` + `IdCodec` |

## 2. 客户端能力约束

目标架构必须服从客户端实际能力，以下约束优先于 REST 纯度：

- Web 使用 axios，支持 `GET`、`POST`、`PUT`、`DELETE`、`PATCH`。
- Mobile 的统一请求入口只接受 `'GET' | 'POST' | 'PUT' | 'DELETE'`（`aio-life-mobile/src/services/api.ts`），微信小程序等平台的请求 API 也不保证支持 `PATCH`。
- 因此全站只使用 `GET`、`POST`、`PUT`、`DELETE` 四种方法。
- 局部更新使用 `PUT /resources/{id}`，并在 DTO 和接口文档中明确：**字段缺省表示不修改，显式 `null` 表示清空（仅在该字段支持清空时）**。这是平台约束下的相对最优，不用 `PATCH`。
- 批量删除不使用带请求体的 `DELETE`，统一使用 `POST /resources/batch-delete`，避免不同客户端和代理对 `DELETE` body 的支持差异。

如果未来移动端请求库和所有目标平台都稳定支持 `PATCH`，再把局部更新迁移为 `PATCH`，本文其余规则不变。

## 3. 模块边界

保留现有顶层模块划分，不拆分 `record`，也不要求调整其内部包结构。

`record` 是核心个人数据域，当前 82 个 Controller 中有 47 个在其中，`capture`、`config`、`feedback`、`system`、`bankcard`、`sso`、`scheduling` 等模块已经依赖它。拆分或重排没有明确收益：

- 当前没有独立部署、独立团队或跨项目复用需求。
- Controller 对 Service 的依赖深度有限（最多 4 个，绝大多数 1–2 个），不存在必须靠拆分解决的耦合。
- 接口不一致是写法问题，不是模块边界问题；拆模块不能替代接口规范，不拆也不妨碍统一接口。

模块边界保持现状，其他顶层模块也不因本文调整。新增能力落在已有对应模块，不为整理目录做跨模块搬迁。

## 4. 资源与 URL

### 4.1 命名规则

- 路径使用 **kebab-case 复数名词**：`/goals`、`/anniversary-records`、`/honor-records`、`/time-records`、`/bank-cards`。
- 一个 Controller 对应一个资源；不得使用 `ExpController` 这类缩写类名，也不得让类名与路径不一致。
- 路径变量统一为 `{id}`；只有真正的子资源才使用 `{parentId}` 形式。
- 路径中不出现动词，除第 4.4 节列出的明确动作子资源。
- 两个 Controller 不得使用完全相同的基础路径；子资源使用独立的嵌套基础路径（例如 `/wardrobe/items` 与 `/wardrobe/categories`）。

### 4.2 标准端点

| 操作 | 形态 | 返回 |
| --- | --- | --- |
| 管理列表 | `GET /resources` | `PageResp<XxxVO>` |
| 选择器数据 | `GET /resources/options` | `List<OptionVO>` |
| 详情 | `GET /resources/{id}` | `XxxDetailVO` |
| 创建 | `POST /resources` | `XxxVO` |
| 局部更新 | `PUT /resources/{id}` | `XxxVO` |
| 删除 | `DELETE /resources/{id}` | `Void` |
| 批量删除 | `POST /resources/batch-delete` | `BatchResult` |
| 状态子资源 | `PUT /resources/{id}/pin` | `XxxVO` |
| 排序 | `PUT /resources/order` | `List<XxxVO>` |
| 非幂等动作 | `POST /resources/{id}/sync` | `XxxVO` |

管理列表、选择器数据和详情是三种不同的读模型，不能用同一个接口返回不同结构。

### 4.3 列表的三种形态

1. **管理列表**：`GET /resources`，可分页，返回 `PageResp<XxxVO>`。用于表格、管理页、需要总数的场景。
2. **选择器数据**：`GET /resources/options`，不分页，返回轻量 `OptionVO { value, label }`。用于下拉框、关联选择、首页快捷入口；服务端必须保证有界并设置数量上限。
3. **详情**：`GET /resources/{id}`，返回完整 `DetailVO`。

禁止再出现 `/query`、`/page`、`/list`、`/all`、`/my` 这类列表别名。目标、纪念日、里程碑等天然小集合也必须使用上述三种形态之一，不能返回第四种裸 `List<VO>`。

### 4.4 子资源与动作

- 子资源使用嵌套基础路径：`/expenses/{expenseId}/device`、`/wardrobe/items`。
- 状态和动作使用固定后缀：
  - `PUT /resources/{id}/pin`，请求体 `{ "pinned": true }`，幂等设置，不用 toggle。
  - `PUT /resources/order`，请求体 `{ "ids": ["..."] }`，幂等排序。
  - `POST /resources/{id}/sync`，非幂等动作，例如第三方同步。
  - `POST /resources/{id}/cancel`，非幂等动作，例如取消导出任务。
- 不允许 `POST /{id}/toggleTop`、`POST /reSort`、`PUT /pinned-order` 这类同一语义的多种写法。

### 4.5 管理端

- 管理端必须是独立的 `XxxAdminController`，基础路径统一为 `/system/<resource>`。
- 管理端 Controller 在类级别使用 `@SaCheckRole("admin")`，不在方法上零散标注。
- 用户端 Controller 不出现 `/admin` 子路径，也不出现同一路径因角色不同而语义不同的情况。
- 当前 `/system-config`、`/menu/admin`、`/cbti/admin`、`/feedback/admin` 等特殊入口统一收口到 `/system/*`。

### 4.6 用户私有资源

- 不使用 `/me`、`/my` 前缀；用户归属由登录态隐式确定。
- 例如数据导出使用 `/data-exports`，而不是 `/me/data-exports`；反馈使用 `/feedback`，而不是 `/feedback/my`。
- 归属校验在 Guard/Service 内完成，Controller 不根据路径推断归属。

## 5. HTTP 方法语义

| 方法 | 用途 | 幂等 | 返回 |
| --- | --- | --- | --- |
| `GET` | 读取列表、选项、详情 | 是 | `ApiResponse<...>` |
| `POST` | 创建、批量删除、非幂等动作 | 否 | 创建返回 VO；批量返回 `BatchResult`；动作返回 VO |
| `PUT` | 局部更新、状态设置、排序 | 是 | 更新返回 VO；删除类返回 `Void` |
| `DELETE` | 删除单个资源 | 是 | `Void` |

补充规则：

- 创建和更新都返回更新后的完整 VO，避免客户端二次 GET。
- 删除返回 `Void`；需要知道删除结果时用批量接口的逐项结果。
- `PUT` 在这里表示“按请求体应用局部修改”，不是全量替换；全量替换场景当前不存在，如出现另行定义。
- 不使用 `PATCH`、`HEAD`、`OPTIONS` 作为业务接口。

## 6. 分页、排序与筛选

分页参数、页大小上限和日期格式继续以 [API 参数规范](API参数规范.md) 为准，本文补充以下更严格的要求：

- 只接受 `page/pageSize`，页码从 1 开始，`1 <= pageSize <= 200`。
- **offset 分页必须返回 `total`**。如果某个资源的总数计算成本过高，就改用游标分页，不得返回 `total: null` 让客户端猜测是否还有下一页。
- 游标分页使用 `cursor/pageSize`，用于日志、存储对象、大流量变更流等场景。
- 默认 `pageSize` 可按资源不同（例如 10、20、50、100），但必须在 Query DTO 上声明并在接口文档中说明；上限统一不超过 200。
- 排序统一使用 `sort=field,asc` 的重复参数形式；字段必须走白名单，服务端始终追加唯一 ID 作为稳定排序的次级键。
- 日期筛选：本地日期使用 `[startDate, endDate]` 闭区间；日期时间使用 `[startTime, endTime)` 左闭右开，避免边界重复。
- 筛选字段平铺在具体的 Query DTO 上，不使用 `CommonQuery<T>` + `condition` 的泛型容器。

## 7. DTO 与类型边界

每个资源固定四类模型：

```
XxxListQuery     实现 PageQuery          // page、pageSize、筛选、sort
XxxCreateCmd     创建命令                // 只包含可写字段
XxxUpdateCmd     更新命令                // 字段可缺省，缺省表示不修改
XxxVO            列表/写操作返回模型
XxxDetailVO      详情返回模型
OptionVO         选择器返回模型
```

规则：

- 请求和响应模型放在 `api` 模块内，持久化 Entity 只在模块内部流转，不得出现在 Controller 签名中。
- 转换统一由 MapStruct Convertor 完成，一个模块一个 Convertor，不在 Controller 里手写字段拷贝。
- 所有 `@RequestBody` 必须 `@Valid`；创建 DTO 的必填字段在 DTO 上声明，更新 DTO 不做无条件必填。
- 日期时间在 DTO 中使用 `LocalDate`/`LocalDateTime`，序列化格式全局配置，不在每个字段写格式字符串。
- 对外枚举使用稳定的字符串 code，不使用整数魔法值；Jackson 统一序列化。
- 公开接口禁止 `Map<String,Object>`、`JsonNode` 作为响应模型。确实需要透传第三方动态结构时，放在第三方适配代码中（如 `record/client`），并包一层命名 schema。
- 请求 ID 字段一律使用 `String`，不做数值转换。

## 8. ID 与当前用户

- 边界层所有 ID 使用 `String`：路径变量、查询参数、请求体、响应体一致。
- 使用统一 `IdCodec` 在边界解码和校验；Service 内部使用 `long`，非数值 ID（UUID、Neo4j elementId）由 `IdCodec` 保留原格式。
- 全局 Jackson 配置把 `Long` 序列化为字符串，不依赖每个 VO 手写注解。
- Controller 不调用 `StpUtil`。通过 `@CurrentUserId String userId` 参数解析器注入当前用户，Service 显式接收 `userId`，便于测试且没有隐式上下文。
- 归属校验放在 Guard 或 Service：`requireOwned(userId, id)`；Controller 不做权限判断，也不根据请求参数设置归属字段。

## 9. 错误模型

建立领域异常体系，Controller 不捕获业务异常：

```
ApiException(code, httpStatus, message)
├── NotFoundException        404
├── ForbiddenException       403
├── ConflictException        409
├── ValidationException      400/422
└── RateLimitException       429
```

规则：

- 全局 `@RestControllerAdvice` 统一映射异常；未预期异常返回 500，不泄漏堆栈、SQL 和内部类名。
- 字段校验错误在 `data` 中返回稳定的 `{ field: message }` 结构，客户端按字段展示。
- HTTP 状态表达错误类别，`code` 保留业务细分。推荐使用语义化 HTTP 状态；如果团队决定保留“统一 HTTP 200 + 业务码”，只需把下表的 HTTP 列改为 200，其余规则不变。
- 禁止在 Controller 中 `return ApiResponse.error(...)`；所有错误通过异常表达。
- 业务码沿用现有 `ResponseCodeConst` 分类，本文只补充 NotFound、Forbidden、Conflict 等缺失类别。

| 场景 | 推荐 HTTP | 业务码类别 |
| --- | --- | --- |
| 参数格式或校验失败 | 400 / 422 | 参数错误 |
| 未登录或登录失效 | 401 | 未登录 |
| 无权限、非本人资源 | 403 | 禁止访问 |
| 资源不存在 | 404 | 不存在 |
| 状态冲突、重复创建 | 409 | 冲突 |
| 触发限流 | 429 | 限流 |
| 未预期异常 | 500 | 通用失败 |

## 10. 鉴权与归属

- 管理员接口只存在于 `XxxAdminController`，类级 `@SaCheckRole("admin")`。
- 用户接口依赖全局登录拦截，不在每个 Controller 写 `@SaCheckLogin`。
- 公开路径只在 `SaTokenConfig` 维护一份 allowlist，禁止散落的 `@SaIgnore`。
- 二级密码等路由级校验使用注解 + AOP，在接口边界生效，不在业务方法内手写判断。
- 资源归属校验在 Guard/Service 内完成，查询条件始终带当前用户，不信任请求中的用户字段。

## 11. 批量与动作

- 批量删除：`POST /resources/batch-delete`，请求体 `{ "ids": ["..."] }`，`@NotEmpty` 校验，单次上限 200。
- 批量创建或批量更新：`POST /resources/batch`，返回逐项结果，不复用单条接口循环调用。
- 批量结果使用统一结构：

```java
record BatchResult(int success, int failed, List<ItemError> errors) {}

record ItemError(String id, int code, String message) {}
```

- 批量操作允许部分成功，返回失败项及原因；全量事务回滚只在业务明确要求时使用，并在文档中说明。
- 状态类操作必须是幂等设置，不允许 toggle；客户端发送目标状态，服务端重复执行结果一致。
- 动作接口返回受影响的资源，便于客户端更新本地状态。

## 12. 响应与文件

- 所有业务响应使用 `ApiResponse<T>`；所有管理列表使用 `PageResp<T>`；错误通过异常表达。
- 文件、图片、导出下载统一返回 `ResponseEntity<Resource>`，由 `FileResponse` 工具构造，负责 `Content-Type`、`Content-Length`、`Content-Disposition`、`ETag`、`Cache-Control` 和 `Range`。
- Controller 不直接写 `HttpServletResponse`；`ResponseEntity<byte[]>` 只用于小体积代理响应。
- 公开图片允许缓存，使用 `Cache-Control: public, max-age=...`；私有文件使用 `private, no-store`。
- 上传只有一个入口：`POST /files`，返回 `FileVO`；业务资源只引用文件 ID，不直接处理 MultipartFile。

## 13. Controller 模板与禁则

```java
@Tag(name = "目标")
@RestController
@RequestMapping("/goals")
@RequiredArgsConstructor
@Validated
public class GoalController {

    private final GoalService goalService;
    private final GoalConvertor convertor;

    @GetMapping
    @Operation(summary = "分页查询目标")
    public ApiResponse<PageResp<GoalVO>> list(
            @CurrentUserId String userId, @Valid @QueryParams GoalListQuery query) {
        return ApiResponse.success(goalService.list(userId, query).map(convertor::toVO));
    }

    @GetMapping("/{id}")
    @Operation(summary = "查询目标详情")
    public ApiResponse<GoalDetailVO> detail(
            @CurrentUserId String userId, @PathVariable String id) {
        return ApiResponse.success(convertor.toDetail(goalService.get(userId, IdCodec.decode(id))));
    }

    @PostMapping
    @Operation(summary = "新增目标")
    public ApiResponse<GoalVO> create(
            @CurrentUserId String userId, @Valid @RequestBody GoalCreateCmd cmd) {
        return ApiResponse.success(convertor.toVO(goalService.create(userId, convertor.from(cmd))));
    }

    @PutMapping("/{id}")
    @Operation(summary = "更新目标")
    public ApiResponse<GoalVO> update(
            @CurrentUserId String userId, @PathVariable String id,
            @Valid @RequestBody GoalUpdateCmd cmd) {
        return ApiResponse.success(
                convertor.toVO(goalService.update(userId, IdCodec.decode(id), convertor.from(cmd))));
    }

    @DeleteMapping("/{id}")
    @Operation(summary = "删除目标")
    public ApiResponse<Void> delete(
            @CurrentUserId String userId, @PathVariable String id) {
        goalService.delete(userId, IdCodec.decode(id));
        return ApiResponse.success();
    }

    @PostMapping("/batch-delete")
    @Operation(summary = "批量删除目标")
    public ApiResponse<BatchResult> batchDelete(
            @CurrentUserId String userId, @Valid @RequestBody BatchDeleteCmd cmd) {
        return ApiResponse.success(goalService.batchDelete(userId, cmd.ids()));
    }

    @PutMapping("/{id}/pin")
    @Operation(summary = "设置目标置顶状态")
    public ApiResponse<GoalVO> pin(
            @CurrentUserId String userId, @PathVariable String id,
            @Valid @RequestBody PinCmd cmd) {
        return ApiResponse.success(
                convertor.toVO(goalService.setPinned(userId, IdCodec.decode(id), cmd.pinned())));
    }

    @PutMapping("/order")
    @Operation(summary = "调整目标排序")
    public ApiResponse<List<GoalVO>> reorder(
            @CurrentUserId String userId, @Valid @RequestBody ReorderCmd cmd) {
        return ApiResponse.success(
                goalService.reorder(userId, cmd.ids()).stream().map(convertor::toVO).toList());
    }
}
```

Controller 硬性禁则：

- 不注入 Mapper，不创建 `LambdaQueryWrapper`，不写事务，不捕获异常。
- 不暴露 `getBaseMapper()`，不提供无注解的 public 辅助重载。
- 不出现 `StpUtil`，不使用 `long`/`Long` 作为路径 ID。
- 一个类只服务一个资源；管理员操作另起 `XxxAdminController`。
- 所有请求体 `@Valid`，所有方法 `@Operation`，类上 `@Tag`。
- Controller 只做参数接收、调用 Service、Convertor 转换和返回封装。

## 14. 契约生成与架构守护

- OpenAPI 由 springdoc 从 DTO 生成；Web 和 Mobile 的类型只从契约生成，不手写重复类型。
- 契约生成脚本和统一推送入口继续使用 [API 参数规范](API参数规范.md#契约生成与验证) 中的约定。
- 在 `aio-life-server` 增加 ArchUnit 规则，把架构约束变成测试：
  - `api..` 不得依赖 `..mapper..` 和 `..entity..`。
  - `@RequestBody` 参数必须带 `@Valid`。
  - `api..` 禁止 `ApiResponse.error`、`Map<String,Object>`、`JsonNode`（第三方适配代码除外）。
  - `@SaCheckRole` 只能出现在 `*AdminController`。
  - 每个 `@RestController` 必须有 `@Tag`，每个 mapping 方法必须有 `@Operation`。
  - 禁止 `getBaseMapper` 和 `StpUtil` 出现在 `api..`。
- 每个资源至少一组集成测试：列表分页、详情 404/403、创建校验、局部更新、批量部分失败。
- 契约测试校验实际路由、方法、参数名和响应结构与 OpenAPI 一致，避免文档与实现漂移。

## 15. 允许保留的差异

只有以下内容可以按资源不同，其余必须统一：

- `pageSize` 的默认值。
- 排序字段白名单。
- 某资源提供 `/options`，还是只提供管理列表。
- 哪些路径进入公开 allowlist。
- 批量操作的单次上限数值，但不得超过 200。

## 16. 明确否决的做法

- 通用 `BaseController<T>` 或通用 CRUD 引擎：会隐藏每个资源的语义，破坏 OpenAPI、权限边界和测试可读性。需要的是模板，不是继承。
- `CommonQuery<T>` + `condition` 泛型容器：让契约生成和 Swagger 失真，改为具体 Query DTO。
- `Boolean` 作为写操作返回值：没有信息量，无法表达部分失败。
- toggle 类接口：非幂等，重试会翻转两次。
- `Map<String,Object>` 作为公开响应：客户端无法生成类型。
- 在 Controller 内拼查询条件：把数据访问决策泄漏到 HTTP 层。
- 同一路径因角色不同而返回不同结构或语义。
- 用 `POST` 伪装删除、用 `GET` 执行写操作。
