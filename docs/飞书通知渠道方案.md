# 飞书通知渠道方案

## 1. 范围

一期只支持 AIO Life 通过用户自己的飞书自建应用机器人，向指定用户单向发送消息。系统不读取飞书消息，也不依赖群聊、OAuth 回调或 WebSocket。

## 2. 最简配置流程

每个 AIO Life 用户维护一套独立的飞书应用凭证：

1. 用户在飞书开放平台创建企业自建应用并启用机器人能力。
2. 为应用开通“获取用户基本信息”（`contact:user.base:readonly`）权限，并在通讯录权限范围中加入通知接收人；权限变更后发布新版本并由管理员审批。
3. 用户在 AIO Life 中只填写 App ID 和 App Secret。
4. 后端使用应用凭证获取 `tenant_access_token`，并读取该应用通讯录授权范围内的用户 `open_id`。
5. 只有一个可见用户时自动将其设为接收人并启用渠道；有多个用户时由用户从列表中选择。
6. 无法读取用户列表时，允许在高级设置中手工填写当前应用下的 `open_id`。
7. 保存后可发送测试消息。

“默认通知创建机器人的用户”无法可靠实现，因为飞书的 App ID/App Secret 不包含应用创建者身份。上述规则用“唯一可见用户自动绑定”实现最少配置；需要默认绑定本人时，应把应用通讯录权限范围只配置为本人。

`open_id` 是应用级身份。同一个飞书用户在不同 App ID 下的 `open_id` 可能不同，不能跨应用复用。更换 App ID 或 App Secret 时，系统必须清除旧接收人并重新发现。

## 3. 数据与安全

`notification_channel_config` 按 `user_id + channel` 唯一，保存：

- 用户自己的 `app_id`；
- AES-GCM 加密后的 `app_secret`；
- 当前应用下的 `receiver_open_id` 和可选接收人名称；
- 渠道启用状态。

安全规则：

- `app_id` 和 `open_id` 可明文存储，`app_secret` 必须加密存储且不会通过 API 返回；
- 加密主密钥来自 `AIO_LIFE_NOTIFICATION_ENCRYPTION_KEY`；
- `tenant_access_token` 仅在服务内存中按 App ID 缓存，不持久化；
- 更换应用凭证时清除旧接收人，避免跨应用使用 `open_id`；
- 真实 App ID、App Secret、访问令牌和用户 `open_id` 不得进入 Git；
- 通知重试载荷使用同一主密钥加密，数据库不保存通知正文明文。

## 4. API

| 方法 | 地址 | 说明 |
|---|---|---|
| `GET` | `/notification/channels/feishu` | 查询当前用户的应用、接收人和启用状态 |
| `PUT` | `/notification/channels/feishu` | 验证并保存凭证、接收人或启用状态 |
| `GET` | `/notification/channels/feishu/recipients` | 查询当前应用可选接收人 |
| `DELETE` | `/notification/channels/feishu` | 删除当前用户的飞书配置 |
| `POST` | `/notification/channels/feishu/test` | 向当前接收人发送测试消息 |
| `GET` | `/notification/preferences` | 查询业务通知偏好 |
| `PUT` | `/notification/preferences` | 更新业务通知偏好 |

## 5. 发送与重试

发送时根据通知所属的 AIO Life 用户加载 App ID、解密 App Secret，并使用对应应用获取 `tenant_access_token`。消息只发送到同一条配置保存的 `receiver_open_id`。

业务通知先写入 Outbox，后台任务异步投递。网络超时、限流和飞书服务端临时错误按 1、5、30、120 分钟退避重试；无效凭证、无权限和无效接收人不自动重试。
