# AIO Life 表结构、代码复用与重构评估

审查日期：2026-09-12。后端版本：`38b2a8d`；前端版本：`d31dfb2`。

本次核对当前全量 DDL、增量脚本、表结构文档，并重点追踪实体、查询、写入、REST/MCP 和前端业务页面。未连接运行中的数据库，未执行迁移、应用测试或性能压测；下文的确定项来自源码与脚本，性能建议仍需实际数据和执行计划验证。没有修改业务代码。

**总体判断：按业务拆表的方向合理，基础设施复用已有基础，但数据不变量和业务规则没有稳定地集中维护。应先修数据正确性与权限，再整理业务服务，最后拆大模块和大页面。**

| 维度 | 评估 | 主要依据 |
|---|---|---|
| 领域建模、拆表 | 基本合理，可继续演进 | 不同生活领域有不同属性与生命周期；金额使用 DECIMAL，核心属性没有全部塞进 JSON |
| 唯一性、关联完整性 | 明显需要加强 | 业务唯一约束被删除；多态关联没有校验目标归属；分类删除未维护历史引用 |
| 索引与迁移 | 不够成熟 | 核心用户查询缺少合适索引；新建与升级生成的约束不同 |
| 技术和展示复用 | 基本合理 | BaseEntity/AuditEntity、统一 requestClient、Dashboard Provider、财务看板等均有实际使用 |
| 业务规则复用 | 不足，已有行为漂移 | 时长多套公式；REST/MCP 规则不同；同一微信读书网关两套 Client |
| 重构方式 | 适合在单体内渐进调整 | 先形成共享业务用例，再调整目录；当前没有必须拆微服务的证据 |

辅助统计：最终全量脚本包含 **55 张表，其中 19 张仅有主键索引**；后端 **481 个 Java 文件**，其中 `record` 占 296 个。55 个 REST Controller 中，24 个直接导入业务 Mapper，25 个存在直接接收 Entity 的请求。前端仅统计 `apps/web-antd/src` 自有代码，共 **234 个 TS/Vue 文件、60,270 行**，不把 Vben 的 packages 计入业务重复。这些数字用于定位，不等同于重复率或质量评分。

## 1. 优先修复：关联归属和可写字段边界

**P1：校验“当前记录属于谁”还不够，必须校验“关联目标属于谁”。**

时迹保存会根据请求中的 `relateId/relateType`，直接读取阅读/影视记录并将未开始状态改为进行中。目标查询与更新只有 ID，没有目标用户条件；新增和修改时迹都会执行。证据：[TimeRecordServiceImpl.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/service/impl/TimeRecordServiceImpl.java:48)。

触发场景：用户创建自己的时迹，传入另一个用户尚未开始的影视或阅读 ID。当前实现可以修改对方记录的状态。这是源码明确可达的路径；本次未对线上数据进行操作。

任务明细也有同类问题：REST 创建明细没有检查父任务归属；关注列表补充任务名称时，直接 `listByIds(taskIds)`。知道他人的任务 ID 时，可通过自己创建的关联明细读取该任务名称。证据：[任务明细创建](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/TaskDetailController.java:73)、[关注列表关联查询](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/TaskDetailController.java:155)。

此外，任务明细 update/reSort 直接把请求 Entity 用作更新对象，WHERE 约束当前用户，却没有限制 SET 中的 `userId/taskId`。演出表甚至直接将 `create_user` 当作所有者；更新 Entity 时允许请求携带新的 `createUser`，可将自己记录的归属改走。证据：[明细更新](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/TaskDetailController.java:88)、[演出更新](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/PerformanceController.java:81)。

建议：

- 为新增、修改、排序分别定义字段有限的请求 DTO；排序只允许 ID 和排序值。所有者、审计字段由服务器决定。
- 建立 `TaskApplicationService.addDetail(userId, command)`、时迹关联解析等共享用例，按 `id + user_id + 有效状态` 校验并操作关联对象。
- 个人业务记录使用明确的 `user_id`，审计字段只表示谁创建/修改。演出表迁移时先由可信的历史 `create_user` 回填 owner，再调整查询。
- 普通主从关系可评估带用户维度的复合外键；多态关联仍须应用层维护。只增加单列外键无法证明父子属于同一用户。
- 补两用户的越权回归测试，覆盖关联创建、关联修改、关注列表、排序和审计字段篡改。

## 2. 优先修复：逻辑删除与唯一性

**P1：不能用“先查再写”替代数据库唯一约束。**

2026-08-19 的脚本删除了用户名、系统配置、API Key、通知配置、偏好、投递等 8 项唯一约束，最终全量结构也没有保留这些约束。注册仍是 `count → insert`；两个不同邮箱并发注册同名账户时，两个请求可能都通过检查。通知偏好、通知投递也使用先查后插，重复数据可导致重复投递或后续单行查询/Map 聚合失败。证据：[删除唯一索引的脚本](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/sql/1_init_table/2026-08-19_drop_logic_delete_unique_indexes.sql:1)、[注册查重](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/sso/service/impl/UserServiceImpl.java:455)、[通知投递去重](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/service/impl/FeishuNotificationServiceImpl.java:312)。

应逐表定义唯一性的生命周期：

| 对象 | 需要明确并落实的约束 |
|---|---|
| 用户名、邮箱 | 是否允许逻辑删除后重新使用；有效账户至少应保持唯一 |
| 用户绑定 | 若每平台只允许一个有效绑定，约束 user_id + platform |
| 通知配置 | 有效 user_id + channel 唯一 |
| 通知偏好 | 有效 user_id + biz_type + channel 唯一 |
| 视频记录 | 当前查重规则对应有效 user_id + bvid 唯一 |
| 用户字典覆盖 | 每个用户对同一 template_id 仅一个有效覆盖 |
| 通知投递 | dedup_key + user_id + channel 的幂等范围与保留期，独立于通用逻辑删除策略 |

如果业务允许删除后重建，可设计可空生成列 `active_slot = CASE WHEN is_deleted = 0 THEN 1 ELSE NULL END`，参与 `UNIQUE(业务键, active_slot)`。同时规范 `is_deleted` 的非空与取值范围，迁移前清理已有重复。不要直接改成 `UNIQUE(业务键,is_deleted)`，因为多条已删除历史会在第二次删除时再次冲突。该方案利用 MySQL 的生成列索引及唯一索引允许多个 NULL 的语义，是本报告的设计建议。[MySQL 唯一索引说明](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)、[MySQL 生成列说明](https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html)。

反方向的不一致也存在：菜单 `path` 仍对全部历史唯一，但业务查重只看未删除记录。删除后重建同路径菜单，应用检查可通过而数据库拒绝。应选择恢复旧记录、有效记录唯一，或明确永久保留路径，并让校验一致。证据：[菜单 path 唯一约束](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/sql/1_init_table/2026-08-18_init_all_tables.sql:177)、[菜单查重](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/system/service/impl/MenuServiceImpl.java:223)。

## 3. 优先修复：账单导入幂等

**P1（本报告按账目准确性提高优先级）：同批次内的重复交易就可能重复入账。**

导入时对交易号执行 `.distinct()`，只去重了用于查询数据库的集合，最终保存的仍是原始列表。数据库此前没有交易 T，而请求包含两条 T 时，两条都能进入保存；并发重复导入也没有数据库约束兜底。证据：[账单批量导入](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/ExpController.java:123)；[支出表](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/sql/1_init_table/2026-08-18_init_all_tables.sql:613)只有主键。

建议将导入变成独立用例：规范交易号和空值，校验批内重复，按明确的“用户 + 来源/账号 + 外部交易号”幂等键保存，并返回新增/重复/失败结果。当前结构未清楚表达来源身份，需要先定义，不能直接把支付方式当成交易来源。单笔录入允许无外部交易号；收入、支出表暂时保留，不必为复用而立即合并。

## 5. 数据库迁移：新建库与升级库约束不同

**P2：需要能验证的版本迁移链，而不仅是按日期摆放 SQL 文件。**

状态字符串化迁移为 goal/read_record/movie/b_video 添加了 CHECK，但最终全量脚本没有任何 CHECK。CI 明确只执行最终全量结构，因此新建库和按增量升级的旧库约束不同。证据：[状态迁移 CHECK](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/sql/1_init_table/2026-09-06_stringify_progress_status.sql:21)、[视频状态 CHECK](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/sql/1_init_table/2026-09-06_stringify_b_video_status.sql:20)、[CI 初始化入口](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/.github/workflows/docker-publish.yml:76)。

另外，后端 AGENTS 指导执行建表目录下全部脚本，而当前 baseline 已合并部分变更；照做会重复加列或删除不存在的索引。CI 已经正确避开重复执行，不能把问题描述成“CI 正在跑全部增量”。

建议明确 baseline 与只用于升级的版本脚本，引入迁移版本及校验记录（可使用 Flyway 等工具）；CI 同时验证空库初始化、旧版本升级，并比较列、索引、约束。表结构文档从最终结构生成，不能只合并 ADD/MODIFY/DROP COLUMN 而遗漏 CHECK 和索引。执行环境的 MySQL 精确版本及已应用迁移记录应纳入盘点。

## 6. 索引：围绕实际用户查询补齐

**P2，性能效果待测：部分核心业务表只有主键，与当前查询方式不匹配。**

例如 expense/income 按用户、日期过滤排序；time_record 只有日期索引，却普遍按用户和日期查询；更新时迹会按 user_id + time_id 删除旧运动明细，而 exercise_record 只有主键。证据：[支出查询](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/ExpController.java:65)、[收入查询](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/IncomeController.java:59)、[时迹查询](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/TimeRecordController.java:74)、[运动明细更新](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/service/impl/TimeRecordServiceImpl.java:144)。

优先评估的候选索引：

| 表 | 候选列 | 对应访问 |
|---|---|---|
| time_record | user_id, is_deleted, date | 用户日/周/月时迹 |
| expense | user_id, is_deleted, exp_time | 支出分页、时间范围 |
| income | user_id, is_deleted, inc_date | 收入分页、时间范围 |

这些是验证起点，排序列是否加入、列顺序和现有索引替换需看数据分布与 EXPLAIN。不要只因表有 user_id 就批量加同一种索引。年度日期过滤目前还有 LIKE 前缀写法，建议改为明确的起止日期范围后一起检查执行计划。

## 7. 分类：明确停用、删除和历史引用

**P2：分类多套并存本身不是问题，生命周期规则缺失才是问题。**

衣柜删除父分类时，没有检查有效子分类或衣物引用；树只从根分类连接子节点，会使仍有效的子分类消失在树上。衣物仍保留 category_id，查询名称却只读取未删除分类，因此历史记录会失去分类显示。证据：[衣柜分类删除](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/wardrobe/service/impl/WardrobeCategoryServiceImpl.java:61)、[分类树构建](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/wardrobe/service/impl/WardrobeCategoryServiceImpl.java:101)、[衣物分类名称](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/wardrobe/service/impl/WardrobeItemServiceImpl.java:172)。

建议对已引用分类优先提供停用；删除时阻止有引用的分类、迁移到用户选定分类，或在确需历史展示时保存名称快照。外键只能保证行存在，不能自动解决逻辑删除后查询不可见的问题。

用户字典的公共模板与个人覆盖方式适合个性化，应保留；补齐每用户每模板有效覆盖唯一性。时迹分类有统计属性，衣柜分类有树结构，不应为了“减少表数量”全部塞进 user_dict_data.ext_data。可复用颜色/图标选择、排序、树操作等稳定部分。

## 8. 后端复用：把共享业务用例放到服务层

**P2：已有通用 CRUD，但缺少共享的业务规则。**

TaskServiceImpl 主要转发基础操作，ExpenseServiceImpl 为空壳；用户归属、字段默认值、关联写入、批量事务散落在 Controller。MCP 一部分直接调用 Controller，一部分直接访问 Mapper，另一些调用 IService 后仍在工具入口独立实现规则。证据：[TaskServiceImpl.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/service/impl/TaskServiceImpl.java:18)、[ExpenseServiceImpl.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/service/impl/ExpenseServiceImpl.java:16)、[RecordMcpTools.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/mcp/RecordMcpTools.java:37)。

具体漂移：

- B 站 REST 统计未学习时长直接 total-watch，MCP 使用 max(total-watch,0)；异常进度数据下两入口不一致。[REST 视频统计](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/BVideoController.java:148)、[MCP 视频统计](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/mcp/BVideoMcpTools.java:68)。

建议围绕明确用例建立服务：添加任务明细、重排任务、保存荣誉与附件、更新视频进度、获取视频统计。服务承担权限、默认值、领域约束和事务；REST/MCP 仅转换输入输出。单纯将 Controller 的 Mapper 换成 IService，或再加一个万能 BaseController，不能解决这些问题。不同入口可保留不同 VO 和显示文案。

## 9. 审计复用：统一填充，但不混入所有权

**P2：已有 BaseEntity/AuditEntity，实际写入仍不一致。**

BaseEntity 提供手动 fillCreate/fillUpdate；IncomeEntity、ExpenseEntity 自己重新定义审计字段，新增/修改有的设置、有的只依赖数据库时间默认值，操作人字段可能缺失。当前没有 MetaObjectHandler 自动填充实现。证据：[BaseEntity.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/core/pojo/entity/BaseEntity.java:27)、[ExpenseEntity.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/pojo/entity/ExpenseEntity.java:83)、[ExpController.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/ExpController.java:86)、[IncomeController.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/IncomeController.java:74)。

可统一审计能力及更新策略，按需要接入 MyBatis Plus 自动填充；同时处理非请求场景的任务执行人，避免后台作业无条件依赖登录上下文。自动填充不能代替 DTO 字段白名单，也不能把 create_user 自动当成 owner。保留 AuditEntity 对特殊主键/日志实体的适配，不强迫所有表继承同一个庞大实体。

## 10. 外部平台：收敛同平台 Client，保留业务聚合差异

**P2：微信读书两份客户端属于明确应合并的重复。**

WeReadClient 与 WereadClient 请求同一网关、同一 skill_version，同样访问 /readdata/detail；前者给首页卡片，后者给阅读同步。两份使用不同 HTTP/JSON 栈、超时和错误策略；后者有端点清单、429 处理和外部错误隔离，修复需要维护两处。证据：[WeReadClient.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/client/WeReadClient.java:38)、[WereadClient.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/weread/WereadClient.java:29)。

合并为一个平台网关 Client，负责版本、鉴权、超时、限流错误转换和响应类型；卡片聚合与同步流程继续独立。保留现有同步中的游标推进和连接版本校验，不要在合并时丢失。GitHub、LeetCode 中散落在 Provider/Service 的直接 HTTP 调用也可按平台逐步收敛，无需一开始设计适用于所有平台的同步继承框架。

账号绑定的唯一性、凭证更新和缓存失效也应进入绑定服务：当前 UserBindController 直接知道 GitHub 的可见缓存键，更新非 weread 平台时只失效旧平台，其他平台改成 github 可留下旧的不可见缓存。证据：[UserBindController.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/api/UserBindController.java:115)。平台身份可选择不可修改或显式迁移，并统一处理受影响缓存。

## 11. 前端复用：统一契约、更新流程，再拆页面

**P2：展示组件已有复用，页面中的业务状态规则仍重复。**

财务已有共享 TransactionDashboard，但收入删除同时刷新列表和统计，支出删除只刷新列表；看板无法自动感知这次变更，可能继续显示已删除金额。证据：[收入删除](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-front/apps/web-antd/src/views/my-hub/income/index.vue:238)、[支出删除](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-front/apps/web-antd/src/views/my-hub/expense/index.vue:339)。建议统一财务 mutation 完成后的局部更新与统计失效流程；保留支出导入、交易明细等业务差异。

API 类型也没有成为统一来源：goal.ts 使用 number ID，time-tracker.ts 把 userId/createUser 标为 number，违背 string ID 契约；todo API 已定义 Task/Detail，页面和编辑器又定义近似类型。证据：[goal.ts](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-front/apps/web-antd/src/api/core/goal.ts:6)、[time-tracker.ts](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-front/apps/web-antd/src/api/core/time-tracker.ts:11)、[todo.ts](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-front/apps/web-antd/src/api/core/todo.ts:23)。这证明契约漂移，不能仅凭类型错误断言线上已经发生精度损失。应分别定义响应 DTO、创建/修改请求和表单模型，统一 string ID、分页结构和日期序列化，减少 any 掩盖的问题。

时迹主页面 2,888 行、编辑表单 1,476 行只是线索；真正的拆分依据是它们混合了分类映射、统计、查询、拖拽几何与监听、碰撞和多种视图。先抽时段领域函数，再抽分类适配器、查询 composable、交互 composable，最后拆日/周/月展示组件。否则只是把耦合从一个文件搬到多个文件。

保留并推广 requestClient、TransactionDashboard、CodingDashboardLayout、AuthImage/ImageUpload/useAuthImageUrl；账单和豆瓣导入解析已拆为纯函数并有测试，也可作为模式参考。当前没有证据支持重写 Vben packages 或建设全量 CRUD 元框架。

## 12. 通知和模块边界：逐步整理

**P2/P3：通知共享的是同一业务事件，渠道可靠性却分成两条路径。**

LeetCode 先循环旧 NotificationSender，再单独调用飞书通知；飞书负责持久化去重与重试，邮件和站内信并未共享同等机制；邮件 sender 还硬编码每日题业务类型。证据：[LeetcodeServiceImpl.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/service/impl/LeetcodeServiceImpl.java:187)、[EmailNotificationSender.java](/Users/hurry/Documents/GitHub/lys1313013/aio-life/aio-life-server/src/main/java/top/aiolife/record/notification/EmailNotificationSender.java:35)。建议一个 NotificationService.publish 管偏好、业务类型、幂等和投递状态，渠道适配器只负责发送。保留 message 作为站内信、notification_delivery 作为投递记录，这两种表的职责可以清晰区分，无需合表。

record 同时承载时间/任务、财务、内容、文件、邮件、平台绑定和同步；sso 依赖 record 的邮件服务，record 的邮件服务又依赖 sso 的日志实体/Mapper，存在包依赖环。这里是源码包边界问题，不代表已经发生 Spring Bean 循环注入故障。

在同一个应用内渐进形成 identity、notification、storage、integrations，以及时间/任务、财务、阅读影视等业务模块。先解决上述用例和权限边界，再随业务改动搬包；不应先做一轮无行为收益的大规模目录迁移。

## 建议实施顺序与验收

| 阶段 | 工作范围 | 完成标准 |
|---|---|---|
| 第一批：数据正确性 | 关联归属、DTO 白名单、有效唯一性、账单幂等、时迹规则 | 两用户隔离通过；批内及并发重复不新增；所有时长入口一致 |
| 第二批：结构可靠性 | baseline/迁移分离与校验、关键索引、分类生命周期、明确 owner | 新建库与升级库约束一致；有执行计划证据；停用分类不破坏历史展示 |
| 第三批：业务复用 | Task/TimeRecord/BVideo 等用例服务；REST/MCP 共用；批量事务与审计 | 同一命令的权限、默认值和统计一致；故障时业务与附件/排序不部分成功 |
| 第四批：降低维护成本 | 微信读书 Client、通知渠道、财务刷新、前端 DTO 与 composable、渐进拆包 | 修复一个领域规则只需修改一处，跨入口回归覆盖其行为 |

数据库修改前需要盘点现有重复、空 owner、孤立关联及迁移历史；清理和回填完成后再添加约束。索引收益、真实数据规模和线上迁移状态仍待验证。本次保留现有业务实现，仅产出评估报告。
